    CISSP Domain 1 — Security and Risk Management（セキュリティとリスク管理）

    版：1.0 / 調査基準日：2026-09-12 / 用途：普段の復習用参考書

    公式範囲：ISC2の2024年4月15日発効版。確認日の公式掲載ではDomain 1の比重は16%。本書は独自に整理した学習ノートであり、ISC2の公式教材や本試験の採点基準を再現したものではありません。公式試験範囲

    読み方：最初は第0章で判断の軸を確認し、第1〜12章を公式範囲の順に読みます。その後は目次・検索・比較表から必要な節へ戻ってください。各章の「説明できるか」は、選択肢を見ずに判断理由を思い出すための問いです。試験直前用の圧縮版ではありません。

    重要度：Core（中核）は必須の土台、High Priority（重点）は個人の要注意論点または応用上重要な領域、Supporting（補完）は周辺知識です。これは本書の編集上の区分で、ISC2が公表する細目別の出題頻度ではありません。

    履歴の扱い：個別回答を再確認できたQ95〜98、今回の会話に提供された学習要約、111問完了時の過去の総括を統合しました。全111問の原文・回答を逐一取得できたわけではありません。「誤答・要注意」は要約上の重点を含み、個別の誤答を断定できないものがあります。未確認は未出題と同義ではありません。根拠は問題履歴台帳、範囲は網羅性確認表をご覧ください。

    0. 判断の基礎 — Exam Perspective（試験での考え方）

    重要度：High Priority（重点） / 関連：全領域

    0.1 管理者視点を、設問の条件に結び付ける

    Managerial Perspective（管理者視点）とは、事業に必要な保護水準を組織として決定・維持する視点です。技術を軽視する意味ではありません。セキュリティは事業目標を達成するための手段であり、停止・費用・使いにくさも含めたリスクを比較します。

    判断軸 確認すること 適用例 過剰な一般化を避ける
    Business First（事業を踏まえる） 守る業務と、達成したい結果は何か 販売停止が致命的なら可用性も重視 収益のために法令や人命を犠牲にしない
    Risk-based Decision（リスクに基づく判断） 脅威・影響・既存対策・許容範囲は何か 評価結果から対策を選ぶ 評価済みなのに最初から調査をやり直さない
    Policy / Process before Technology（方針・プロセスを先に定める） 要件・責任・承認・運用があるか 未定義の権限ルールを製品だけで解決しない 緊急時は承認済み手順で直ちに封じ込める
    Accountability（説明責任） 誰が結果を引き受けるか 事業責任者が残余リスクを受容する 外注先へ作業を委託しても責任がすべて消えるわけではない
    Proportionality（比例性・釣り合い） 対策の強さが影響に見合うか 重要情報へ強い保護、低リスクには簡素な管理 安さだけで必要な保護を省かない

    CISSPの学習上は「経営層が方向性・資源・責任を持つ」を基本にします。ただし、責任者がすべての実務を行うわけではありません。担当者に実行を委任し、承認経路と結果の確認を残すのが管理です。

    0.2 FIRST / BEST / MOST / PRIMARYの読み分け

    設問語 日本語 判断の入口 よくある誤り
    FIRST 最初に 現在地点を特定し、次の行為に必要な前提を探す 最終的に必要な対策を早すぎる段階で選ぶ
    NEXT 次に すでに済んだ工程を除外する 方針承認後に、方針承認を再び選ぶ
    BEST 最も適切 明示された目的・制約・権限を最も満たすもの 最も強い製品、最も長い選択肢を選ぶ
    MOST effective 最も効果的 対象のリスクや原因へ最も効くもの 実装が簡単な対策と混同する
    PRIMARY 主たる目的・責任 直接達成する結果、最終的な責任を探す 副次的効果を主目的と取り違える
    LEAST / EXCEPT 最も低い／例外 否定の向きを先に固定する 正しい説明を見つけて反射的に選ぶ

    実践する読み方は、①役割、②段階、③守る対象と目的、④制約、⑤設問語、の順で短く整理することです。「自分の現場なら」という追加条件は持ち込みません。

    例：新規SaaS（クラウド提供ソフトウェア）を採用したい。 要件が不明なら、まずデータ・業務・法的要件とリスクを確認します。要件と評価が済み、残余リスクの承認を求められているなら、権限を持つ事業責任者の判断へ進みます。漏えいが進行中で担当者に緊急対応権限があるなら、方針文書の新規作成より、承認済み手順に沿う被害抑制が適切です。同じサービスでも段階によって答えが変わります。

    Common Trap（よくあるひっかけ）：「常に経営層へ報告」「必ずリスク評価が最初」「技術的な選択肢は誤り」という万能ルールは使いません。安全確保、法的義務、設問の役割、すでに終わった工程を優先して読みます。

    0.3 問題から一般原則を取り出す

    個別の題材 再利用する原則 本書の参照先
    年間損失額を計算した 数値を求めた後に対策後リスクと年間費用を比較する 9.3・9.4
    BIAの最初の作業を間違えやすい 技術の復旧順ではなく業務影響を根拠に優先順位を作る 7.2
    OwnerとCustodianが紛らわしい 要件・承認を決める側と、実施する側を分ける 3.2
    RAIDやVPNの目的を問われた 製品名より、その場面で保護する性質を特定する 2.1
    米国法名を取り違える 業種だけでなく対象主体・情報・活動・管轄を見る 4.2

    説明できるか：承認済みの復旧計画に従う担当者に「経営層の承認を毎回得る」が常に最適とは限らない理由を説明してください。

    1. Professional Ethics（職業倫理）

    重要度：Core（中核） / 公式対応：1.1

    1.1 ISC2の倫理と専門職としての行動

    Ethics（倫理）は、法的に許される行動の中でも専門職として何を選ぶかを導きます。法律を守るだけで、利益相反の隠蔽や能力の誇張が正当化されるわけではありません。

    ISC2の4つのCanon（倫理原則）は、学習用に言い換えると、①社会・公共の利益・信頼・基盤を守る、②誠実で公正かつ責任ある合法的行動、③依頼者へ注意深く有能な業務提供、④専門職の発展と信用を支える、です。原文と申立手続はISC2倫理規程で確認できます。

    場面 望ましい判断 理由
    上司が監査証拠の改ざんを指示 拒否し、適切な内部経路・法務へ相談する 忠誠心は不正行為への服従ではない
    診断業務が自分の能力を超える 能力の限界を説明し、適任者の支援を得る Competence（専門能力）に応じた提供責任
    見積審査で候補企業に経済的利害がある Conflict of Interest（利益相反）を開示し、審査からの除外等を検討 判断の公平性と信用を守る
    脆弱性を発見した 許可範囲と合意した開示経路に従う 追加の無断侵入は倫理的調査の延長ではない

    1.2 Organizational Code of Ethics（組織の倫理規程）

    組織の規程は、贈答、利害関係、情報の扱い、相談窓口、違反時の手続を実務へ落とします。経営層の行動、通報者保護、公平な調査、継続的な教育が伴って初めて機能します。違反を報告した人を罰する文化では、問題が隠れ、経営判断に必要な情報が届きません。

    Exam Perspective（試験での考え方）：顧客・雇用主の利益だけで完結させず、公共の安全・合法性・誠実性も考えます。倫理違反の疑いがあることと、調査なしで有罪扱いすることは区別します。

    Common Trap（よくあるひっかけ）：NDA（秘密保持契約）があれば法定報告義務までなくなる、公益目的なら無許可の攻撃が許される、という選択肢は慎重に扱います。

    説明できるか：正しい報告経路を使うことが、無差別に外部公開することと異なる理由を説明してください。

    2. Security Concepts（セキュリティの基本概念）

    重要度：Core（中核）、CIAの文脈判断はHigh Priority（重点） / 公式対応：1.2

    2.1 CIAと追加の保護特性

    特性 意味と主目的 主な手段 問題での見分け方
    Confidentiality（機密性） 許可のない開示・閲覧を防ぐ 暗号化、アクセス制限、最小開示 誰が読めるか、盗聴・漏えい
    Integrity（完全性） 不正な変更・破壊を防ぎ、正確さを維持する 変更管理、入力検証、改変検知、署名 内容が変わっていないか
    Availability（可用性） 必要時に正当な利用を可能にする 冗長化、容量確保、復旧、耐障害性 停止・遅延・使えない
    Authenticity（真正性） 主体や情報源が本物であること 本人確認、認証、証明書の検証 本当にその人・発行元か
    Nonrepudiation（否認防止） 行為や送受信を後から否認しにくくする 電子署名、信頼できる時刻・証跡 「送っていない」と主張されたら証明できるか

    同じ対策が複数の特性に貢献することがあります。暗号化だけで完全性が必ず保証されるわけではなく、認証付き暗号など方式・設定に依存します。Digital Signature（電子署名）は改変検出と署名者の確認を支えますが、鍵の安全な管理や身元の結び付きが壊れると、否認防止の証拠力も弱まります。

    2.2 Authentication / Authorization / Accountabilityを分ける

    Identification（識別）は名乗り、Authentication（認証）はその主張の確認、Authorization（認可）は実行してよい行為の決定、Accounting（利用記録）は行為の記録です。Accountability（説明責任）には、個人へ帰属できる識別、適切な認証、改変から保護された記録、責任の割当てが必要です。

    仕組み 直接の役割 単独では足りないこと
    MFA：Multi-Factor Authentication（多要素認証） 異なる要素で認証を強化する 業務権限を適切に決めること
    ACL：Access Control List（アクセス制御リスト） 許可・拒否を実施する アクセス権の事業上の妥当性を承認すること
    Audit Log（監査ログ） 誰が何をしたかの証拠を残す 共有IDで行われた操作の実行者を確実に識別すること
    Hash（ハッシュ値） 基準との相違を検出する 基準値とデータの両方を攻撃者が置換した場合の真正性

    MFA（多要素認証）は、パスワードと秘密の質問のように同じKnowledge Factor（知識要素）を二つ使うだけでは成立しません。複数の領域にまたがる詳細は、将来のDomain 5に委ねます。本章では認証と認可の役割を押さえます。

    3. Security Governance（セキュリティの統治）

    重要度：Core（中核）、役割・注意義務はHigh Priority（重点） / 公式対応：1.3

    3.1 事業戦略と組織の意思決定

    Governance（統治）は、方向・優先順位・責任・監督を定めることです。Management（管理）はその方向に沿って計画し、資源を配分し、実行・測定することです。Security Strategy（セキュリティ戦略）は事業のMission（使命）、Goals（目標）、Objectives（具体的な到達点）へ結び付けます。

    階層 典型的な内容 セキュリティの例
    Strategic（戦略） 長期の方向・投資判断 安全に海外事業へ進出する
    Tactical（戦術） 戦略を実現する計画・プログラム 越境データ移転とアクセス管理を整備する
    Operational（運用） 日々の実施・監視 権限を付与し、ログと例外を確認する

    Steering Committee（運営委員会）は事業・IT・法務・人事などの利害調整に有効です。報告では「重大脆弱性100件」だけでなく、「どの事業が、どれだけの期間、どの影響にさらされるか」「誰の判断が必要か」を示します。

    3.2 誰が決め、誰が実施するか

    役割 主に決める・担うこと 実施・連携 試験での境界
    Senior Management（経営層） 方針、リスクの方向、資源、最終的な監督 事業責任者・CISOと判断 セキュリティ部門だけへ全責任を押し付けない
    Board（取締役会） 経営の監督、重大リスクの監視 経営層から報告を受ける 日々の設定変更担当ではない
    CISO（情報セキュリティ責任者） プログラムの企画・調整・助言・報告 技術・法務・人事・事業と協働 すべての事業リスクの受容権限を自動的に持たない
    Risk Owner（リスク所有者） 担当リスクの対応と、権限内の受容 対策担当へ実施を依頼 リスクを負う業務の責任者を探す
    Data Owner（データ所有者） 分類、保護要件、アクセス承認 事業上の価値を理解し要件を提示 要件・判断・承認が中心
    Data Custodian（データ管理担当者） 所有者の要件に従う保管・運用 バックアップ、設定、技術的保護 実装・維持が中心
    System Owner（システム所有者） システムのライフサイクルと保護の責任 運用・開発・情報所有者と連携 Data Ownerと同一とは限らない
    User（利用者） 許可された利用、ルール遵守、異常報告 教育受講・適切な取扱い 自分に権限があることと再配布の許可は別
    Auditor（監査人） 独立した評価と報告 証拠を調査し、是正を追跡 自分が運用する統制を独立監査したとしない

    RACI（責任分担表）では、Responsible（実行責任）、Accountable（最終的な説明責任）、Consulted（相談先）、Informed（報告先）を分けます。一つの決定で最終責任を曖昧にしないため、Accountable（説明責任者）を明確に置きます。組織によって役職の名称は違っても、意思決定権限と実施責任の区別は変わりません。

    Problem-derived Insights（問題演習由来の知見）：Q36の要注意点を、「データを毎日扱う人ほどOwner」という誤解から切り離します。管理担当者が分類ラベルを設定しても、その分類基準と業務上の許可を決めるのは通常Owner（所有者）です。GDPRのController（処理目的・手段の決定主体）は法律上の役割で、社内のData Ownerと自動的に一致しません。

    3.3 Due Care / Due Diligence（相当な注意／適切な調査・継続確認）

    概念 焦点 例 見分ける問い
    Due Care（相当な注意） 合理的に求められる保護を実際に行う 適切な権限管理、承認済みの保護措置 必要な注意を払って行動したか
    Due Diligence（適切な調査・継続確認） 判断前の調査と、保護の有効性の継続確認 買収前の評価、対策状況の監査、リスク再評価 十分に調べ、機能し続けるか確かめたか
    Negligence（過失） 必要な注意義務に反したこと 既知の重大リスクを権限も根拠もなく放置 義務・違反・因果関係・損害を文脈で見る

    「実施」と「確認」の対比は学習に役立ちますが、法的な意味は管轄や事案に依存し、二つの活動は重なります。Due Diligence（適切な調査）は導入後の確認だけに限定しません。買収前・委託前の調査も代表例です。

    3.4 買収・売却・組織再編

    Acquisition（買収）では価格・製品機能だけでなく、過去の事故、契約、知財、データの利用目的、負債となるシステム、ID連携、既存の統制を調べます。統合時にネットワークを直結すると、未評価の相手側リスクを自社へ持ち込む可能性があります。

    Divestiture（事業売却）では、残す情報・渡す情報、権利、保管義務、アカウント、暗号鍵、再委託、移行中のサービス水準を定義します。「売却したから全部削除」「便利だから共有IDを残す」は両極端です。法務・事業・ITで移行と終了条件を合意します。

    3.5 Framework（枠組み）を目的で選ぶ

    枠組み・規格 主な使い道 混同しない対象
    ISO/IEC 27001:2022（ISMS要求事項） ISMS：Information Security Management System（情報セキュリティ管理体系）を構築・改善し、適合を評価 製品の安全性認証ではない
    ISO/IEC 27002:2022（管理策の指針） 管理策の選択・実施を理解する 27001と同じ認証要求事項ではない
    ISO/IEC 27005:2022（情報セキュリティリスク管理指針） リスクの評価・対応を支える 特定の計算式だけを強制する規格ではない
    NIST CSF 2.0（サイバーセキュリティ枠組み） 経営と現場が目標・現状・差を共有する 技術設定一覧や単一の認証制度ではない
    NIST RMF（リスク管理枠組み） システムの管理策と運用承認をライフサイクルへ組み込む CSFと同じ手順ではない
    NIST SP 800-53（セキュリティ・プライバシー管理策集） 管理策を選び、調整する際の参照 全項目を全システムへ無条件適用しない
    COBIT 2019（企業の情報・技術の統治と管理） 事業目標とITの統治・管理を接続する 個別製品の設定標準ではない
    SABSA（事業に基づくセキュリティアーキテクチャ） 事業要件から設計・サービス・測定へ追跡可能にする 製品名や脅威一覧ではない
    PCI DSS（決済カード情報の保護基準） カード情報環境の保護と適合 一般的な法律そのものではない
    FedRAMP（米国連邦クラウドのリスク・承認プログラム） 連邦機関で使うクラウドの評価・承認に関係する どの顧客のどの業務でも安全を保証するものではない

    ISOは公開された概要・版情報を参照しました。有料規格全文を取得して条項ごとに照合したわけではありません。ISO 27001、27002、27005、COBIT、SABSA、GSAのFedRAMP紹介

    3.6 CSFとRMFの深掘り

    CSF 2.0は、Govern（統治）、Identify（特定）、Protect（保護）、Detect（検知）、Respond（対応）、Recover（復旧）の6機能で成果を整理します。順番に一度ずつ終える工程表ではなく、継続して働く機能です。Current Profile（現状プロファイル）とTarget Profile（目標プロファイル）の差を、事業上の優先順位に従って埋めます。Tier（実践の段階）はリスク統治・管理の厳密さを表し、単純な点数や認証合否ではありません。NIST CSF 2.0

    RMFは、Prepare（準備）→Categorize（分類）→Select（選定）→Implement（実装）→Assess（評価）→Authorize（承認）→Monitor（監視）で理解します。評価者は管理策を調べ、Authorizing Official（承認権限者）は証拠と残余リスクを基に運用を承認します。技術者が「問題なし」と言うだけでは承認になりません。NIST SP 800-37 Rev.2

    Currency（最新性）：古い教材の「CSFは5機能」「RMFは準備を含まない6段階」を、現在版の説明として使いません。ISO 27001は2022版に2024年の気候変動関連追補があります。本書で追補の詳細暗記は求めません。

    説明できるか：管理策の評価に合格したシステムでも、リスクの受容判断が別に必要な理由を説明してください。

    4. Legal / Regulatory / Compliance（法律・規制・遵守）

    重要度：Core（中核）、法の適用対象・GDPRはHigh Priority（重点） / 公式対応：1.4

    4.1 適用対象を判断するための地図

    法律名を見たら、①Jurisdiction（管轄）、②対象主体、③対象情報、④対象の活動、⑤契約上の義務、を分けます。組織の所在地だけでは決まりません。顧客の所在地、処理対象、越境移転、委託関係で追加の義務が生じ得ます。

    義務の種類 成り立ち 例 誰と確認するか
    Law（法律） 立法に基づく義務 個人情報保護、犯罪、知財 法務
    Regulation（規則・規制） 法に基づく監督機関の詳細要件など 業種別の保護義務 法務・コンプライアンス
    Contract（契約） 当事者が合意した義務 SLA、通知、監査権、損害責任 法務・調達・事業
    Industry Standard（業界標準） 業界の共通基準 PCI DSS 契約当事者・適合担当
    Internal Policy（内部方針） 組織の意思決定 情報分類、持出し制限 経営層・規程管理者

    Compliance（遵守）は必要な条件を満たすこと、Security（セキュリティ）はリスクを適切に管理することです。チェック項目に適合しても、範囲外のサービスや新しい攻撃で損害が起きることがあります。反対に、技術的に安全でも無許可の個人情報利用が合法になるわけではありません。

    Exam Perspective（試験での考え方）：「一番厳しい規則を選べばよい」だけでは解けません。規則が衝突する場合、法務と管轄・優先関係・合法的な代替案を整理します。契約で強行法規を消すことはできません。

    名称 主な対象・目的 判断の手がかり よくある取り違え

    GLBA：Gramm-Leach-Bliley Act（グラム・リーチ・ブライリー法） 対象金融機関の顧客情報のプライバシー・保護 金融商品・サービスと顧客情報 FISMAと混同しない
    SOX：Sarbanes-Oxley Act（サーベンス・オクスリー法） 対象上場企業等の財務報告・内部統制 財務報告の信頼性、経営者の認証 全情報の機密性を直接規定する一般法ではない

    PCI DSS：Payment Card Industry Data Security Standard（決済カード業界データセキュリティ基準） カード会員情報等を扱う対象環境と、その安全へ影響する構成 カード処理・保存・伝送、関係するサービス 政府が制定した法律そのものではない

    4.3 GDPRとPrivacy（プライバシー）

    GDPR：General Data Protection Regulation（一般データ保護規則）では、Personal Data（個人データ）を取り扱う目的・根拠・範囲・保護・説明責任を考えます。「EUの市民権がある人だけ」が対象なのではありません。EU内の拠点との関係、EU内の人への商品・サービス提供や行動監視など、Article 3（第3条）の条件を確認します。欧州委員会：適用範囲と基本概念

    法律上の役割 意味 セキュリティ上の要点
    Controller（管理者・処理目的等の決定主体） 処理の目的と手段を決める 適法性・透明性・説明責任を確保する
    Processor（処理者・委託処理主体） 管理者のために処理する 指示・契約・安全管理・再委託条件を守る
    Data Subject（データ主体） 個人データが関係する本人 権利行使の対象者
    DPO：Data Protection Officer（データ保護責任者） 要件に該当する組織等で助言・監督・窓口を担う 管理者の責任を丸ごと肩代わりしない

    Privacy（プライバシー）は機密保持だけでなく、本人に関する情報を適切な目的・根拠で使うことも含みます。Purpose Limitation（目的制限）、Data Minimization（データ最小化）、Accuracy（正確性）、Storage Limitation（保存制限）、透明性と説明責任を、収集時から考えます。同意は適法な処理根拠の一つであり、唯一の根拠ではありません。

    権利 何を求めるか 区別の目印
    Access（アクセス・開示） 自分の情報や処理状況を知る 「見せてほしい」
    Rectification（訂正） 不正確な情報を直す 「間違いを直して」
    Erasure（消去） 条件を満たす情報を削除する Right to be Forgotten（忘れられる権利）
    Restriction（処理の制限） 一定の処理を制限する 保管と通常利用を分ける
    Portability（データ可搬性） 条件を満たすデータを利用可能な形式で受け取る・移す 「別サービスへ持ち運ぶ」
    Objection（異議申立て） 一定の処理に異議を示す 消去請求と同じとは限らない

    Q4の重点：Erasure（消去）はすべての情報を無条件に即時消去する権利ではありません。法的義務に基づく保存、法的請求など例外を確認します。削除できない場合でも、理由と処理制限の検討を切り離して考えます。欧州委員会：本人の権利

    漏えい通知の読み方：管理者から監督機関へは、本人の権利・自由へのリスクが生じそうにない場合を除き、不当に遅滞せず、可能なら認識後72時間以内に通知します。本人への通知は高いリスクの場合に不当に遅滞なく行うという別の条件です。「事故発生後72時間以内に全員へ通知」とまとめません。GDPR本文：第3・5・6・15〜22・33〜34条

    CPPAのFAQ、南アフリカ情報規制当局、日本の個人情報保護委員会。PIPLについては、中国本土の人への商品・サービス提供や行動の分析等で域外の組織も関係し得ること、外国移転に追加の条件があることを押さえます。中国当局の法律本文取得はできず、香港の公的な個人情報保護当局の解説で補完しました。現行の移転閾値や詳細手続の網羅的な法的検証は行っていません。香港PCPD：PIPLの解説

    Transborder Data Flow（国境を越えるデータ移転）は、サーバー所在地だけでなく、海外からのアクセス、再委託先、バックアップ、サポート、削除まで確認します。Data Residency（データ所在）、Data Sovereignty（データに及ぶ法的支配）、Data Localization（国内保存などの要求）を同じ意味で使いません。

    GDPRでは、第三国移転についてAdequacy Decision（十分性認定）、SCC：Standard Contractual Clauses（標準契約条項）、BCR：Binding Corporate Rules（拘束的企業準則）などの条件・根拠を検討します。暗号化は保護措置であり、移転の法的根拠を自動的に作るものではありません。欧州委員会：国際移転の条件

    Common Trap（よくあるひっかけ）：「EU向けサービスではない」「データを匿名化したつもり」「海外リージョンを使っていない」といった一条件で、全義務がないと判断しません。Pseudonymization（仮名化）と、本人の再識別が合理的にできないAnonymization（匿名化）も区別します。

    保護 主に守るもの 成立・維持の考え方 試験の手がかり

    4.6 サイバー犯罪・漏えい・輸出入管理

    Cybercrime（サイバー犯罪）では、不正アクセス、詐欺、情報の窃取・破壊などを、権限・目的・行為・管轄で評価します。Data Breach（データ侵害）は窃取だけでなく、適用法によって不正な開示や喪失等も含みます。通知、契約上の連絡、証拠保全、通常業務の回復を並行調整します。

    Import / Export Controls（輸出入管理）は暗号製品、ソフトウェア、技術情報などに関係します。国・品目・用途・利用者・移転形態を確認し、ライセンスや例外の条件を調べます。米国EAR：Export Administration Regulations（輸出管理規則）のENC（暗号品目の許可例外）にも分類・報告等の条件があります。「強い暗号はすべて輸出禁止」「ダウンロードなら輸出ではない」という単純化を避けます。15 CFR 740.17

    説明できるか：カード情報を扱う病院で複数の保護要件が同時に関係する理由と、それらを一つの法名だけで処理できない理由を説明してください。

    5. Investigation Requirements（調査の要件）

    重要度：Core（中核） / 公式対応：1.5

    5.1 調査は目的・権限・基準を先に定める

    同じ漏えいでも、雇用上の処分、民事上の損害、刑事責任、規制違反、業界標準の適合は別の問題です。一つの事件で複数の調査が並行し得ます。

    種類 主な目的・主体 必要な基準・権限 学習上の識別
    Administrative（社内・行政的調査） 組織の規程違反を人事・管理部門等が確認 適法な監視、社内規程、公平な手続 就業規則や組織の処分
    Criminal（刑事調査） 捜査機関が犯罪と刑罰を扱う 捜査権限、令状等の法的手続、厳格な証拠 国家による訴追
    Civil（民事調査） 当事者間の権利・責任・損害を扱う 開示・保存・裁判手続 損害賠償や契約紛争
    Regulatory（規制当局の調査） 監督当局が規制遵守を確認 当局の権限、報告義務、業種規制 監督・制裁・是正命令
    Industry Standards（業界標準に関する調査） 決済等の適合や事故を関係機関が確認 契約・基準・指定された評価手続 PCI等の義務との対応

    米国法を前提とする基礎問題では、刑事のBeyond a Reasonable Doubt（合理的な疑いを超える立証）と、民事のPreponderance of Evidence（証拠の優越）が対比されます。世界中のすべての民事・規制手続に同じ基準が適用されるわけではありません。基準は管轄と事件の種類を確認します。

    5.2 証拠を使える状態に保つ

    Evidence（証拠）は、Relevant（関連性がある）、Authentic（真正である）、Reliable（信頼できる）だけでなく、適法に取得・保存され、扱いを説明できる必要があります。フォレンジックの道具を先に動かすと、権限外の個人情報を取得したり、証拠を変更したりするおそれがあります。

    概念 目的 実務で残す情報
    Chain of Custody（証拠の管理履歴） 誰が・いつ・なぜ・どのように扱ったかを説明する 取得者、移送、受渡し、保管、アクセス
    Legal Hold（法的保存措置） 関連証拠を通常の削除から保全する 対象、通知先、停止する削除、解除権限
    Integrity Verification（完全性検証） コピーや証拠の変化を検出する 取得時・検証時のハッシュ、使用手段、時刻
    Order of Volatility（揮発性の順序） 消えやすい情報を優先して取得する メモリ、接続、実行状態などの取得判断
    Documentation（記録） 再現・説明・検証を可能にする 操作内容、設定、時刻ずれ、担当、例外

    ライブシステムは電源断でメモリ情報が失われる一方、稼働継続は被害を拡大し得ます。「常に即電源断」「常に稼働維持」という固定回答は使いません。安全・権限・証拠・業務影響を承認済みの手順に沿って調整します。NISTのフォレンジック資料も、適用法について経営・法務と調整することを前提にしています。NIST SP 800-86

    Exam Perspective（試験での考え方）：Domain 1では、調査の目的・権限・要求を押さえます。具体的なディスク取得コマンドや詳細分析はDomain 7の領域です。社員だから私物端末を自由に調べてよい、という結論は出しません。

    Common Trap（よくあるひっかけ）：ハッシュが一致しても、不適法な取得、管理履歴の欠落、取得前の改ざんまで解決したわけではありません。Legal Hold（法的保存措置）中は、通常の保存期間を過ぎても関連証拠の自動削除を止める必要があります。

    説明できるか：漏えいの原因調査を急ぐときに、最初に調査権限と証拠保全手順を確認する価値を説明してください。

    6. Security Documentation（方針・標準・手順・指針）

    重要度：Core（中核） / 公式対応：1.6

    6.1 文書の役割を目的と粒度で比較する

    文書 答える問い 義務性の基本 作成・承認・実施の典型 例
    Policy（方針） 何を守り、なぜ行うか 必須 責任部門が起案、経営層等が承認、全対象者が遵守 機密情報へのアクセスを業務上必要な者へ限定する
    Standard（標準） 何を必須条件にするか 必須 専門部門が定義、権限者が承認、担当が実装 特権アクセスでは承認された多要素認証を必須にする
    Procedure（手順） どの順で実施するか 適用対象は原則必須 運用部門が作成・維持、担当者が実施 申請確認→承認→付与→確認→記録
    Guideline（指針・推奨事項） どの方法が推奨されるか 通常は推奨 専門部門が提示、状況に応じて利用 強い認証の利用者向け推奨例
    Baseline（最低基準・標準構成） 最低限どの状態にするか 組織で定めた適用条件に従う 標準を実装可能な構成へ具体化 サーバーの初期構成と禁止設定

    具体的な文書名・承認者は組織ごとに異なります。Policy（方針）と名付けた文書に設定値が書かれる場合もありますが、試験では記述が担う役割を優先します。Guideline（指針）が契約・規程へ取り込まれ必須化される場合もあるため、義務性は名称だけでなく適用関係を確認します。

    6.2 文書を実装し維持する

    文書化の流れは、適用要件と対象の明確化→利害関係者との調整→責任者・承認→周知・教育→実装→遵守確認→変更・例外管理です。発行して終わりではありません。

    管理項目 なぜ必要か
    Owner（文書責任者）と承認者 誰が解釈・更新・例外判断をするか明確にする
    Scope（適用範囲）と対象者 子会社・委託先・私物端末への適用を曖昧にしない
    Version（版）・施行日・改訂履歴 古い手順の誤使用を避ける
    Review（見直し） 法令・脅威・業務の変化を反映する
    Exception（例外）の期限と代替措置 例外が恒久的な抜け道になることを防ぐ
    Evidence（実施証拠） 受講記録・承認・設定・監査で実装を確認する

    Exception（例外）は、理由・対象・リスク・Compensating Control（代替管理策）・承認権限・期限・再評価を記録します。「技術的にできないので黙って除外」は正式なリスク受容ではありません。

    Exam Perspective（試験での考え方）：「すべての社員へ適切な利用を求める」はAUP：Acceptable Use Policy（許容利用方針）、「新規アカウントの登録作業の順番」はProcedure（手順）です。抽象度と目的を分けると、選択肢の語感に左右されません。

    説明できるか：方針に細かな製品画面の操作まで埋め込むと、長期的な運用が難しくなる理由を説明してください。

    7. Business Continuity（事業継続）の要求

    重要度：High Priority（重点） / 公式対応：1.7

    7.1 BCP / DRP / Incident Responseの関係

    Business Continuity（事業継続）は、混乱が起きても、重要な製品・サービスを許容される水準で継続・再開するための能力です。すべての業務を平常時と同じ水準で直ちに復旧することが目的ではありません。人の安全を確保し、限られた資源を重要業務へ配分します。

    計画・活動 主目的と範囲 主な関与者 成功の尺度
    BCP：Business Continuity Plan（事業継続計画） 人・場所・取引先・情報・ITを含め重要業務を続ける 経営層、業務責任者、BC担当、各部門 重要サービスを許容水準で提供できる
    DRP：Disaster Recovery Plan（災害復旧計画） 被災したIT・施設等を回復させる計画。CISSPではIT復旧の文脈が中心 IT復旧担当、システム所有者、施設等 必要な資源・データを復旧目標内で回復
    Incident Response（インシデント対応） セキュリティ事故を検知・封じ込め・対処・復旧する 対応チーム、法務、広報、関係部門 被害抑制と安全な業務回復
    Crisis Management（危機管理） 重大な状況で全社の意思決定と対外調整を行う 経営層、危機管理、広報 安全・信頼・意思決定の一貫性

    DRP（災害復旧計画）は事業継続を支える一つの計画として理解します。BCPの定義を「サーバーの修理」に縮めると、代替要員、手作業、通信、仕入れ、顧客対応が抜けます。BCPには事前準備だけでなく、発動後の業務継続・再開の行動も含まれます。「事前の対策はすべてBCP、有事の行動はすべてDRP」という分類はしません。

    Problem-derived Insights（問題演習由来の知見）：Q22・Q23に加え、完走時の総括ではQ41・Q53・Q56・Q66・Q67・Q76がBCP／DRP関連の重点として挙がっていました。個々の設問は再取得できていないため、正誤を追加で断定せず、目的・順序・時間目標の境界をまとめて補強しています。

    7.2 BIA（事業影響分析）は業務から資源へ進む

    BIA：Business Impact Analysis（事業影響分析）は、業務が中断した場合の影響と、その時間的変化を把握し、復旧要求・優先順位を導く活動です。Risk Assessment（リスク評価）が「どの脅威がどれほど起こり得るか」を扱うのに対し、BIAは「止まるとどう困り、いつまで耐えられるか」に焦点を置きます。両者を組み合わせて事業継続の戦略を選びます。

    段階 確認すること 主な成果
    準備 経営の支援、目的、対象、担当、調査方法 合意された分析範囲
    業務と影響 重要サービス、停止時の金銭・安全・契約・信用への影響、時間経過 重要度と許容できない影響の境界
    必要資源と依存 人、場所、データ、システム、認証、通信、取引先 業務と資源の対応表
    復旧要求・優先 業務目標に必要な順番と回復時間 承認可能な復旧優先順位と目標

    この整理は、NIST SP 800-34の「業務と重要度→必要資源→資源の復旧優先」の考え方と整合させたものです。NIST SP 800-34 第3.2節

    Q23の読み直し：履歴要約には「BIAの順序・資産価値算定」が要注意とあります。ただし、原選択肢を取得できていないため「BIAは必ず資産価格の算定から」と一般化しません。事業価値・重要度の把握は必要ですが、システム購入価格だけでは優先順位は決まりません。安全上重要な安価なシステムが、高価な非重要システムより先になることもあります。

    例：受注業務を復旧する。 受注アプリだけ復旧しても、IdP：Identity Provider（認証基盤）、DNS（名前解決）、通信回線、決済、倉庫連携が使えなければ注文は完了しません。復旧は「高価なサーバー順」ではなく、業務を成立させる依存関係と必要な水準に従います。

    7.3 RTO / RPO / MTDを時間の意味で区別する

    用語 問うこと 決める根拠 例
    MTD：Maximum Tolerable Downtime（最大許容停止時間） 業務は全体としてどこまで停止に耐えられるか 事業への許容不能な影響 受注停止は8時間が限界
    MTPD：Maximum Tolerable Period of Disruption（最大許容中断期間） 中断の影響が許容不能になるまでの期間 業務・サービスの耐えられる期間 継続管理で用いられる関連概念
    RTO：Recovery Time Objective（目標復旧時間） どれくらいで資源・サービスを回復すべきか 業務要求、依存関係、実現可能性 4時間以内にシステムを回復
    RPO：Recovery Point Objective（目標復旧時点） どの時点までのデータへ戻せる必要があるか 許容できるデータ損失 直前15分までの記録を回復
    WRT：Work Recovery Time（業務再開に要する追加時間） IT回復後、業務確認や処理再開にどれくらい必要か 確認・再入力・再開準備 確認と再処理に2時間

    MTD（最大許容停止時間）とMTPD（最大許容中断期間）は関連しますが、採用する規格・教材の定義を確認します。RTOの対象に「システム復旧だけ」を含めるか「業務再開まで」を含めるかでも、追加時間の数え方が変わります。

    学習用の時間モデル：RTOがIT復旧だけ、WRTがその後の業務再開時間なら、RTO + WRT ≤ MTD を満たすように計画します。現実には不確実性の余裕も必要です。この式をすべての規格で必ず同じ意味の恒等式として扱わないでください。

    例：MTD 8時間、ITのRTO 4時間、WRT 2時間なら、残り2時間が計画上の余地です。RPOが15分でも「15分でサービスが復旧する」意味ではありません。RTOは未来の回復までの時間、RPOは過去のどこまでのデータを回復するかです。

    設計の確認：RPO 15分の要求に、1日1回のバックアップだけでは通常対応できません。レプリケーション（複製）でも破損や不正変更を即時に複製する危険があるため、改変から保護された履歴と復旧確認を組み合わせます。

    Exam Perspective（試験での考え方）：事業側が必要水準を示し、IT側が実現可能性・費用・制約を返します。現行バックアップが24時間間隔だからRPOも24時間、と要件を逆算して正当化しません。満たせなければ差と対応計画を意思決定者へ示します。

    7.4 外部依存と継続戦略

    External Dependencies（外部依存）には、電力、通信、物流、決済、クラウド、部材、人員派遣、建物、共有認証などがあります。契約先を二つにしても、同じ地域、上位回線、クラウド基盤へ依存していれば同時に止まります。これがCommon-mode Failure（共通原因故障）の問題です。

    戦略の例 向いている条件 注意点
    手作業・代替手段 最低限のサービスを簡易に続けたい 処理能力、誤り、後日の照合が必要
    代替要員・相互訓練 特定個人への依存が大きい アクセス権と承認経路も準備する
    複数供給元 一社停止の影響が大きい 上流供給網や輸送の共通依存を確認
    代替拠点 施設停止へ備える 距離、同時災害、利用者の移動を考慮
    クラウドの分散構成 復旧時間を短縮したい コスト、データ整合性、契約、運用複雑性

    Supporting（補完）として、Hot Site（稼働準備の整った代替拠点）は一般に復旧が速く高コスト、Cold Site（設備等を別途用意する代替拠点）は遅く低コスト、Warm Site（中間的な準備の拠点）はその間です。ただし名称だけでRTO達成は保証できず、データ・人員・回線・手順の準備を確認します。

    7.5 要求の実装・演習・改善

    要求を優先付けしてから戦略を選び、経営が費用と残余リスクを判断し、計画・契約・資源・教育へ落とします。計画の担当者が起案・維持を行っても、重要な事業継続方針と資源配分の承認は権限を持つ経営側の責任です。Exercise（演習）では紙面の整合性だけでなく、連絡先、意思決定権限、手作業、外部事業者との協力、データの利用可能性を確かめます。

    確認方法 何を確かめるか 限界
    Read-through（読み合わせ） 計画の誤り・連絡先・役割 実際に復旧できるかは十分に分からない
    Tabletop（机上演習） シナリオに沿う判断と部門連携 本番資源の動作を証明しない
    Simulation（模擬演習） 想定環境での動作と判断 模擬条件と本番の差がある
    Parallel Test（並行試験） 通常業務を続けて代替環境を動かす 全面切替の全リスクは再現しない
    Full Interruption（全面停止・切替試験） 実際の切替に近い総合動作 業務影響が大きく、慎重な承認と戻しが必要

    最も現実的な試験を常に最初に選ぶわけではありません。目的・リスク・成熟度に応じて段階的に検証し、Lesson Learned（得られた教訓）を計画・BIA・契約へ戻します。人命の保護は試験中も優先します。

    説明できるか：復旧サーバーの起動成功と、BCPの成功が同じでない理由を、依存関係・データ・人員の3点から説明してください。

    8. Personnel Security（人的セキュリティ）

    重要度：Core（中核）、職務分離はHigh Priority（重点） / 公式対応：1.8

    8.1 雇用・配置・退職を一つのライフサイクルで管理する

    段階 目的と対応 担当の連携 ひっかけ
    Screening（採用前確認） 職務のリスクに比例した身元・経歴確認 人事・法務・採用部門 無制限な調査や差別を許容しない
    Hiring（採用） 職務・守秘・権利・遵守事項を合意 人事・法務・管理者 技術アクセスだけで責任を定義しない
    Onboarding（受入れ） 業務上必要な権限を承認後に付与、教育・機器配布 上長・所有者・IT 前任者の権限を丸ごと複製しない
    Transfer（異動） 新職務の権限付与と旧権限の見直し 旧・新上長、人事、IT 追加するだけのPrivilege Creep（権限の累積）
    Termination（退職・契約終了） 適切な時点でアクセス失効、資産回収、引継ぎ 人事・法務・警備・IT 通知より早すぎる失効や、終了後の放置

    退職時の順序と時刻は、人事・法務・安全上の要件と整合させます。敵対的な退職では同時性が重要になる一方、すべての退職者を同じ手順で扱うとは限りません。アカウントの削除と無効化を区別し、調査・保存義務のある記録や業務データを不用意に消しません。

    Problem-derived Insights（問題演習由来の知見）：再確認した完走時総括ではQ109のTermination Process（退職・終了プロセス）が誤答論点として挙がっていました。ユーザーの選択肢は未取得のため、具体的な回答番号ではなく、人事通知・失効時刻・資産回収・記録保全の連携へ一般化しています。

    8.2 職務分離と内部者リスク

    概念 目的 例 境界
    Least Privilege（最小権限） 必要最小限の操作に限定 読取業務へ更新権限を与えない 情報を知る業務上の必要性と関連するが同義ではない
    Need-to-know（知る必要性） 特定情報を必要とする者へ限定 人事担当でも担当外の機微情報は見せない 役職の高さだけで全情報へアクセスさせない
    Separation of Duties（職務分離） 一人で不正を完結しにくくする 申請・承認・支払実行を分ける 共謀まで完全に防ぐわけではない
    Dual Control（複数人による共同管理） 重要操作に複数人の関与を要求 高リスクな鍵操作を二者で承認 日常的な別職務への分担とは粒度が異なる
    Job Rotation（職務ローテーション） 属人化を減らし、不正の兆候を発見 担当交代で不自然な帳簿を確認 引継ぎ後の旧権限を残さない
    Mandatory Vacation（強制休暇） 本人不在でも業務を回し、継続的な隠蔽を見つける 他者が担当処理を確認 単なる福利厚生目的の設問と区別

    演習からの一般原則：一人が処理を開始し承認し隠せるなら、認証強化だけでは不正の構造を解消できません。権限・承認・独立した照合を組み合わせます。MFA（多要素認証）は本人以外による利用を減らしますが、本人の不正な権限行使まで防ぐものではありません。

    Insider Threat（内部者の脅威）は悪意だけでなく、過失、疲労、誤操作、侵害された正規アカウントでも生じます。監視は適法性、比例性、通知、アクセス制限と組み合わせ、個人への思い込みで扱いません。

    8.3 契約者・委託先の人にも統制を適用する

    Vendor（供給者）、Consultant（助言者）、Contractor（契約作業者）についても、役割、守秘、必要権限、教育、事故報告、期限、契約終了時の失効を決めます。NDA（秘密保持契約）は情報を秘密として扱う義務、AUP（許容利用方針）は許される使い方を定めるもので、相互に代替しません。

    委託元は、個人の受入れ・監督と、企業としての供給者評価を両方行います。企業の認証があることは、委託先のすべての従業員に自社管理者権限を与える理由にはなりません。供給者全体の管理は第11章

    Exam Perspective（試験での考え方）：人事の通知、業務側の承認、ITの付与・失効を一つの流れにします。「誰が実施したか」と「誰が権限を認めたか」を分けてください。

    説明できるか：異動時に新しい権限だけを足す運用が、退職処理を正しく行っていても危険な理由を説明してください。

    9. Risk Management（リスク管理）

    重要度：High Priority（重点） / 公式対応：1.9

    9.1 Threat / Vulnerability / Riskの因果関係

    用語 意味 Webアプリの例
    Asset（資産） 守る価値があるもの サービス、顧客データ、信頼
    Threat Source / Agent（脅威源・脅威主体） 悪影響を引き起こす可能性のある源 悪意あるハッカー、自然災害
    Threat Event（脅威事象） 損害を生じさせ得る出来事 攻撃者による不正な入力の送信
    Vulnerability（脆弱性） 脅威に利用され得る弱点 未修正の欠陥、不十分な入力処理
    Attack（攻撃） 悪意を持つ主体の具体的行為・手法 SQL Injection（SQLインジェクション）
    Likelihood（発生可能性） その条件で事象と悪影響が生じる見込み 公開状態・攻撃能力・既存対策で変化
    Impact / Consequence（影響・結果） 資産・業務への不利益 Web改ざん、停止、信用低下
    Risk（リスク） 不確実な事象による影響の可能性・大きさ 攻撃が成功し業務へ損失を与えるリスク

    Q95ではユーザー回答C（悪意あるハッカー）が正解でした。一般化すると、人物＝脅威主体、弱点＝脆弱性、手口＝攻撃、損害＝影響と分解できます。ただしThreat（脅威）という語が資料によって主体・事象を広く指すことがあるため、選択肢と問われた粒度を確認します。

    学習上の Risk ≈ Likelihood × Impact は、可能性と影響を組み合わせるモデルです。あらゆるリスクを厳密な掛け算で算出できるという物理法則ではありません。脆弱性の深刻度だけが、その組織の業務リスクを決めるわけでもありません。NIST SP 800-30 Rev.1

    9.2 Scope（範囲）・基準・評価方法

    リスク評価は、組織全体、特定業務、システム、変更、委託など、どの範囲を扱うかをまず明確にします。対象外の前提、評価期間、既存対策、判断基準、関係者を揃えなければ、部署間の「高リスク」を比較できません。

    活動 何をするか 主な成果
    Identification（特定） 資産・脅威・脆弱性・影響を洗い出す リスクシナリオ
    Analysis（分析） 可能性・影響・既存対策を検討する リスクの水準と不確実性
    Evaluation（評価・判定） 定めた基準と比較する 対応の要否・優先順位
    Treatment（対応） 選択肢を決め、実行し、残るリスクを扱う 対応計画・受容判断

    Risk Assessment（リスク評価）は、資料によって特定・分析・評価をまとめた用語です。「分析」と「評価」の訳語だけで順序を機械的に断定せず、何をしているかを見ます。

    方法 入力・出力 長所 限界と試験の目印
    Qualitative（定性） 高・中・低、影響の記述、専門家判断 データ不足でも議論・順位付けしやすい 尺度と判断者のばらつき。高×高を精密な金額にしない
    Quantitative（定量） 頻度・損失額・分布など数値 費用対効果・金銭影響を比較しやすい 数値の精密さと根拠の確かさは別
    Semi-quantitative（半定量） 1〜5などのスコア 一貫した分類を支える 5が1の5倍の損失とは限らない

    Interview（聞き取り）、Workshop（討議）、Checklist（確認表）、Scenario Analysis（シナリオ分析）などを組み合わせます。Delphi Technique（デルファイ法）は匿名の専門家意見を反復して集約し、特定の強い発言者の影響を抑える方法です。

    9.3 AV・EF・SLE・ARO・ALEを判断までつなげる

    記号・英語 日本語 意味・単位 式・例
    AV：Asset Value 資産価値 評価対象の価値、通貨 10,000,000ドル
    EF：Exposure Factor 曝露係数・損失割合 一回の事象で失うAVの割合、0〜1 50% = 0.5
    SLE：Single Loss Expectancy 単一損失予測額 一回あたりの予測損失、通貨／回 SLE = AV × EF
    ARO：Annualized Rate of Occurrence 年間発生率 一年あたりの期待回数、回／年 200年に1回 → 0.005
    ALE：Annualized Loss Expectancy 年間損失予測額 一年あたりの期待損失、通貨／年 ALE = SLE × ARO

    演習Q96〜98の計算：AV = 10,000,000ドル、典型的損失 = 5,000,000ドルなので、EF = 5,000,000 ÷ 10,000,000 = 0.5、SLE = 5,000,000ドルです。ARO = 1 ÷ 200 = 0.005、ALE = 5,000,000 × 0.005 = 25,000ドル／年。回答96:C、97:B、98:Aはいずれも正解と確認できました。

    単位で検算すると、通貨／回 × 回／年 = 通貨／年となります。「200年に1回」をARO 200や0.5にしないこと、損失額がすでに与えられているならそれがSLEに相当することを確認します。

    Q1から拡張する費用対効果：

    年間純便益 = 対策前ALE − 対策後ALE − 対策の年間総費用

    本書独自の例として、対策前ALE 120,000ドル、対策後ALE 30,000ドル、年間費用40,000ドルなら、年間損失の削減は90,000ドル、年間純便益は50,000ドルです。ALEが120,000ドルだから「120,000ドルまでどんな対策費も合理的」とは言えません。対策後にも損失が残るからです。

    年間費用にはライセンス、運用、教育、保守、検証、業務負担などを含めます。初期費用を複数年へ配分する場合は期間を明示し、期間の違う金額をそのまま引きません。設問が初期費用しか与えない場合、勝手な償却年数を追加しないでください。

    Deep Dive（深掘り）：ALEは長期的な平均のモデルで、翌年に必ずその額を失う意味でも、最悪損失の上限でもありません。AROは年間の期待回数なので1を超え得ます。1年に少なくとも一回起こる確率とは一般には異なります。低頻度でも組織が存続できない損失は、平均値だけでは判断できません。

    推定値の幅、重大事故の尾部リスク、同時災害、二重計上、法的義務を考えます。感度分析で、頻度や損失が変わっても同じ選択になるか確認します。FAIR：Factor Analysis of Information Risk（情報リスクの要因分析）は、損失頻度と損失規模を分解する定量的な考え方としてSupporting（補完）に位置付けます。特定の数式やモデルの名前だけで良い判断にはなりません。

    9.4 リスク選好・許容度・対応・残余リスク

    概念 意味 判断者・具体化
    Risk Appetite（リスク選好） 目標のために進んで引き受けるリスクの種類・水準 経営の方針として定める
    Risk Tolerance（リスク許容度） 特定の目標やリスクに対する許容できる限界・変動 選好を業務上の指標・閾値へ落とす
    Risk Capacity（リスク負担能力） 組織が耐えられるリスクの限界 財務・人員・法的存続等から考える
    Inherent Risk（固有リスク） 指定した管理策を考慮する前のリスク 何を除外した評価か明記する
    Residual Risk（残余リスク） 対策後に残るリスク 権限者が許容可否を判断する

    「新事業の小規模実証は許す」という選好を、「実証データは匿名のサンプルに限り、損失上限と中止条件を置く」という具体的な許容範囲へつなげます。Appetite（選好）は好き嫌い、Tolerance（許容度）は我慢強さという日常語だけで覚えないでください。

    対応 何を変えるか 例 誰が決めるか・残るもの
    Acceptance（受容） 対応を追加せず、把握したリスクを引き受ける 低い損失を記録して監視する 権限を持つリスク所有者。無視ではない
    Avoidance（回避） リスクを生む活動をやめる・行わない 機微データを集める事業を中止 事業判断が必要。機会も失う
    Mitigation / Reduction（軽減） 発生可能性・影響を下げる パッチ、権限制御、分散、バックアップ 対策担当が実行し、有効性を評価
    Transfer / Sharing（移転・共有） 主に損失の負担や対応の一部を他者と分担 サイバー保険、契約上の補償 法的責任・信用低下がすべて消えるわけではない

    Cyber Insurance（サイバー保険）では、対象事故、免責、自己負担、限度額、条件、通知、対策義務を確認します。保険が攻撃を防ぐわけではなく、SLA（サービス水準合意）の返金が事業損失を全額埋めるとも限りません。

    残余リスクの扱い：評価結果、対応、残る影響、所有者、承認、期限、再評価条件をRisk Register（リスク台帳）へ記録します。セキュリティ担当が勝手に受容したことにせず、委譲された権限の範囲で処理します。重大変更・事故・新脅威で前提が変われば再評価します。

    Common Trap（よくあるひっかけ）：法律違反を費用対効果だけで受容できるとは限りません。また「リスクは必ずゼロにする」も誤りです。目標は必要な義務を満たし、事業が許容できる水準へ管理することです。

    9.5 Control（管理策）の分類は二つの軸で考える

    実現手段の軸 意味 例
    Administrative / Managerial（管理的） 方針・人・プロセスで管理 身元確認、方針、教育、職務分離
    Technical / Logical（技術的・論理的） ソフトウェアや論理機構で制御 MFA、ACL、暗号化、ログ分析
    Physical（物理的） 物理的な接触・侵入・環境を制御 柵、錠、入退室、消火設備
    機能の軸 目的 例と注意
    Preventive（予防） 事象の発生や成功を防ぐ アクセス拒否、パッチ、施錠
    Detective（検知） 発生・兆候を把握する ログ監視、警報、照合
    Corrective（是正） 問題状態を修正する 原因除去、設定修正
    Recovery（復旧） 必要な能力を回復する バックアップからの復元
    Deterrent（抑止） 行為の意欲を低下させる 監視の掲示、制裁の周知
    Directive（指示） 望む行動を示す 方針、手順、指示標識
    Compensating（代替・補完） 本来の対策が困難な場合、目的を別の手段で満たす 遺産システムへ分離・監視等を組合せる

    この二つの軸は排他的ではありません。防犯カメラはPhysical（物理的）でDetective（検知）的、掲示によりDeterrent（抑止）的にもなります。教育はAdministrative（管理的）で予防に寄与します。NIST等では別の分類体系も使うので、組織・教材の文脈も読みます。

    演習の重点：完走時総括はQ20・Q75・Q100で対策分類を重点に挙げています。まず「何で実現するか」と「何のために働くか」のどちらを聞いているかを確認すると、Technical（技術的）とPreventive（予防）を競合する選択肢として誤比較しなくなります。

    WAF：Web Application Firewall（Webアプリケーション用ファイアウォール）は攻撃成功のLikelihood（可能性）を下げる代表例です。パッチの代替として恒久放置せず、回避、誤検知、未対応の攻撃を評価します。バックアップは主としてデータ喪失や停止のImpact（影響）を軽減しますが、目的と構成によって複数の効果があります。

    9.6 評価・監視・報告・改善を閉じる

    Control Assessment（管理策評価）は、設計が適切か、実装されているか、意図した効果が出ているかを確認します。「製品が設置されている」「規程に書いてある」だけでは有効性の証拠になりません。Security Assessment（セキュリティ評価）とPrivacy Assessment（プライバシー評価）は重なりますが、適法な目的や本人への影響などは別に評価します。NIST SP 800-53 Rev.5

    指標・活動 何を確認するか 例
    KPI：Key Performance Indicator（重要業績・実行指標） 活動が計画通り進むか 期限内の権限棚卸し実施率
    KRI：Key Risk Indicator（重要リスク指標） リスクが高まっていないか 重要資産の未修正期間、復旧試験失敗
    Continuous Monitoring（継続監視） 前提・状態・管理策の変化 構成変化、脆弱性、サービス変更
    Internal Reporting（内部報告） 意思決定と是正を促す 所有者、期限、事業影響、要承認事項
    External Reporting（外部報告） 法令・契約・利害関係者の要求を満たす 当局通知、顧客説明、適合報告

    指標の分類は利用目的に依存します。「教育受講率」は実施指標であり、行動変容や事故減少を単独で証明しません。「検知件数が増えた」も悪化とは限らず、検知能力が改善した可能性があります。母数・対象・測定条件を揃えます。

    Continuous Improvement（継続改善）は、評価→是正→再検証→方針・設計への反映を繰り返すことです。Maturity Model（成熟度モデル）は属人的な対応から、定義・測定・改善される仕組みへの発展を考える道具であり、成熟度の点数が事故ゼロを保証するものではありません。Plan–Do–Check–Act（計画・実行・評価・改善）はこの循環を捉える補助になります。

    9.7 リスク枠組みの使い分け

    全社的な方向付けはCSF・COBIT、管理体系と評価・対応はISO 27001／27005、システムの承認と監視はNIST RMF、事業要件と設計の追跡はSABSA、カード情報環境の義務はPCI DSS、と目的で選びます。同じ企業で併用して構いません。枠組みの比較

    Framework（枠組み）の採用そのものをRisk Treatment（リスク対応）の完了とみなしません。自組織の対象・責任・証拠・対応計画へ落としたことが重要です。

    説明できるか：ALEが減る対策でも採用できない場合と、年間純便益が負でも必要になり得る対策を一つずつ挙げてください。

    10. Threat Modeling（脅威モデリング）

    重要度：Core（中核）、STRIDEの比較はHigh Priority（重点） / 公式対応：1.10

    10.1 対象をモデル化し、起こり得る失敗を考える

    Threat Modeling（脅威モデリング）は、守る対象と前提を可視化し、どんな悪いことが起こり得るか、どう対処し、その対処をどう確かめるかを整理する活動です。運用前に一回だけ行うものではなく、設計・実装・変更・事故を通じて更新します。OWASPの概要

    観点 記述すること 例
    Scope（対象範囲） 守る資産、機能、想定外とする範囲 受注APIと管理画面
    Data Flow（データの流れ） 主体、処理、保管、通信 顧客→API→注文DB
    Trust Boundary（信頼境界） 権限・管理主体・信頼の前提が変わる場所 インターネットとアプリ、委託先との接続
    Assumption（前提） 成り立つと仮定した条件 管理者端末が管理下にある
    Threat / Mitigation（脅威・軽減策） シナリオ、影響、対策 権限検証不足→注文の不正変更→所有者確認
    Validation（妥当性確認） 前提・対策が有効か検証 権限境界の否定テスト、設計レビュー

    DFD：Data Flow Diagram（データフロー図）では、外部主体・プロセス・データストア・データフロー・信頼境界を扱います。ネットワーク配線図だけでは、誰が何を信用しているか、データの利用目的は見えないことがあります。

    10.2 STRIDEを侵害される性質と対応させる

    分類 日本語 主に破られる性質 例・対応の方向
    Spoofing なりすまし Authenticity（真正性）・認証 他人の資格情報の悪用→適切な認証
    Tampering 改ざん Integrity（完全性） 注文金額の書換え→入力・権限・改変検証
    Repudiation 否認 Nonrepudiation（否認防止） 操作を否認→信頼できる記録・署名
    Information Disclosure 情報漏えい Confidentiality（機密性） 他人の情報を閲覧→最小権限・暗号化
    Denial of Service サービス妨害 Availability（可用性） 資源枯渇→制限・容量・分散
    Elevation of Privilege 権限昇格 Authorization（認可） 一般利用者が管理機能へ→権限境界の検証

    Microsoftが整理するSTRIDEは脅威の見落としを減らす分類です。リスクの金額や優先順位を自動的に計算するものではありません。MicrosoftのSTRIDE説明

    Problem-derived Insights（問題演習由来の知見）：STRIDEは完走時総括で比較的理解が進んだ領域でした。正解した用語を再認するだけでなく、たとえばRepudiation（否認）に対して「暗号化」だけで十分か、「個人に結び付く改変困難な記録」が必要かを説明できる状態を目指します。

    10.3 他の手法との使い分け

    手法 主な問い・用途 STRIDEとの違い
    Attack Tree（攻撃ツリー） 目的へ至る条件・経路をAND／ORで分解する 分類ではなく達成経路を表す
    PASTA：Process for Attack Simulation and Threat Analysis（攻撃シミュレーションと脅威分析のプロセス） 事業目的から技術・脅威・弱点・攻撃・リスクを段階的に分析 ビジネスの影響を含む一連の手順
    Misuse / Abuse Case（不正利用のシナリオ） 正常機能をどう悪用できるか 利用場面を通じて要求を見つける
    MITRE ATT&CK（実際の攻撃戦術・技術の知識体系） 現実の攻撃者がどう行動するか 実際の攻撃知識を補う。設計全体のリスク評価の代わりではない
    DREAD（影響・再現性等による評価法） 複数の評価軸で優先を考える 脅威の分類とリスクの採点を区別する補完知識

    PASTAは、事業目標→技術範囲→分解→脅威分析→弱点分析→攻撃のモデル化・模擬→リスクと影響の分析、という7段階で捉えます。公式範囲が特定手法の丸暗記だけを要求している、と読み替えないでください。PASTA開発者側の説明、MITRE ATT&CK

    攻撃ツリーの読み方：「情報を盗む」が最上位の目的なら、「正規IDを悪用する」OR「公開された保存先から取得する」が別経路です。「正規IDを悪用する」経路にパスワードと第二要素の両方が必要ならAND条件になります。一経路の対策だけで他のOR経路も消えたとは言えません。

    Exam Perspective（試験での考え方）：脅威の一覧を作ること、脆弱性を発見すること、業務リスクを評価すること、対策を検証することを区別します。攻撃者視点は有効ですが、対象と許可範囲が定まる前に実攻撃を始めることではありません。

    説明できるか：脅威モデリングを完成した後でも、設計変更時に更新する必要がある理由を説明してください。

    11. Supply Chain Risk Management（供給網のリスク管理）

    重要度：Core（中核） / 公式対応：1.11

    11.1 購入した製品・サービスにもリスクは残る

    SCRM：Supply Chain Risk Management（供給網のリスク管理）は、製品・サービスを作り、運び、組み込み、運用し、終了するまでの依存を管理します。情報機器の直接の供給者だけでなく、部品、開発環境、ソフトウェア依存、更新経路、再委託、クラウド基盤も対象です。

    リスク 例 なぜ通常の受入れ試験だけでは足りないか
    Tampering（改変・細工） 出荷前のファームウェア改変 通常機能が動いても悪意ある挙動が潜む
    Counterfeit（偽造品） 正規品に見せた部品 品質・保守・真正性が確認できない
    Implant（不正な仕込み） ハードウェア・ソフトウェアへ隠した機能 特定条件でのみ動作する場合がある
    Dependency Risk（依存リスク） ライブラリ、ビルド基盤、更新サーバーの侵害 一つの侵害が多数の利用者へ波及
    Concentration Risk（集中リスク） 多くの重要業務が同一供給者へ依存 個別サービスの分散だけでは解消しない
    Lifecycle Risk（継続利用のリスク） サポート終了、倒産、データを取り出せない 購入時の安全性だけで長期運用を保証しない

    供給網の不透明さを前提に、重要性に応じた調査と多層の軽減策を設計します。NIST SP 800-161 Rev.1・2024年更新

    11.2 選定・契約・監視・終了をつなげる

    段階 主な行為 判断・実施する人
    要件化 情報分類、利用目的、必要水準、法令、終了条件を定める 業務所有者・セキュリティ・法務・調達
    選定前 重要性で評価を段階化し、証拠と能力を確認 調達と専門部門、必要なら独立評価者
    契約 最低保護要件、通知、監査権、再委託、SLA、削除・返却を合意 権限を持つ契約当事者
    受入れ 正規流通、真正性、構成、権限、検証を確認 技術担当、受入れ責任者
    運用 事故、変更、評価結果、更新、依存先の変化を監視 サービス責任者と専門部門
    終了 移行、返却・削除、資格情報失効、証拠・記録の保全 業務・法務・IT・供給者

    Third-party Assessment（第三者評価）は、質問票、独立監査報告、認証、テスト、契約、実際の運用証拠を、対象サービスと期間に結び付けて読みます。報告書の対象外機能や、顧客側に要求される統制を見落とさないでください。評価は初回契約時だけで終わらせません。

    11.3 SLA・契約・技術的保証を混同しない

    手段 できること 保証しないこと
    SLA：Service Level Agreement（サービス水準合意） 水準、計測、対象時間、報告、違反時の扱いを合意 停止の物理的防止、すべての損失の補償
    Minimum Security Requirements（最低セキュリティ要件） 認証、ログ、暗号化、更新等の必須条件を定義 文書にあるだけで実装された証明
    SBOM：Software Bill of Materials（ソフトウェア部品表） 構成要素・版・依存関係の把握と影響調査を助ける 脆弱性ゼロ、未記載要素ゼロ、実行時安全性
    Signed Update（署名付き更新） 配布元と改変の検証を助ける 正規の開発・署名環境自体が侵害された場合の安全性
    Silicon / Hardware Root of Trust（半導体・ハードウェアの信頼の起点） 鍵・起動検証等を支える、保護された基礎 システム全体の設定・運用の安全性
    PUF：Physically Unclonable Function（物理的複製困難関数） 製造ばらつき等による個体差を識別・鍵生成等に利用 模倣・解析リスクの絶対的な排除

    Root of Trust（信頼の起点）は、上位の検証を支えるために信頼する必要がある基礎です。基礎を守ることと、供給者・設計・運用全体を無条件に信用することは異なります。NISTのHardware Root of Trust定義

    演習との接続：SLAの知識を、稼働率の数字だけで終わらせません。どのサービス・測定点・除外時間が対象か、インシデント通知が間に合うか、RTO／RPOを支えられるかを確認します。年間稼働率が高くても、繁忙日の数時間停止が事業に致命的な場合があります。

    Exam Perspective（試験での考え方）：外部サービスの利用は、作業の外部化であって判断の放棄ではありません。データ・業務の重要性を定め、責任の分担と証拠を確認し、残るリスクを権限者が判断します。

    説明できるか：SBOMと製品署名を受領しても、供給者の開発・更新プロセスを評価する価値が残る理由を説明してください。

    活動 目的 対象・方法 成果の見方

    ニーズとリスクの把握→対象者と行動目標→教材・方法→実施→測定→改善、の循環で進めます。新人、管理者、開発者、経営層、委託先では必要な内容が違います。経営層には意思決定と責任、開発者には設計・コーディング、利用者には情報取扱いと報告を結び付けます。

    BCPの訓練対象：組織全体には避難・連絡・報告など必要な認識を広げ、計画上の役割を持つ人には担当手順を実行できる訓練を行います。経営層の意思決定、代理担当、必要な外部関係者も役割に応じて対象です。全員に同じ詳細技術訓練を行うことも、IT部門だけへ限定することも適切とは限りません。過去総括ではQ56の解説にBから教材正解Cへの訂正があったことを確認しましたが、選択肢本文は取得できていないため、どの対象者がCだったかは復元していません。Q93・94も啓発・訓練の区別の誤答として総括に挙がっています。

    方法・題材 ねらい 設計上の注意

    測定 読み取れること 単独では言えないこと

    知識確認 内容を理解したか 長期間維持・応用できるか

    報告率・報告時間 適切な行動と対応速度 報告が多いから事故が悪化したという断定

    周期的に見直し、事故、新しい攻撃、業務変更、技術の普及を反映します。Cryptocurrency（暗号資産）では詐欺・鍵管理・送金承認、Blockchain（ブロックチェーン）では記録の改変耐性と入力情報の正しさの区別、AI：Artificial Intelligence（人工知能）では情報入力・出力の扱いを、各自の業務へつなげます。

    12.5 AIをDomain 1の判断へつなげる

    公式ページのAIに関する補足は、倫理・リスク・プライバシー・外部AI供給者の評価を既存Domainへ結び付けています。本節は新たな独立Domainや公表されていない出題比率を追加するものではありません。ISC2のAI補足

    AI利用の論点 Domain 1としての判断
    機密情報や個人情報の入力 利用目的、情報分類、保管・学習利用、再委託、所在地を確認する
    Hallucination（もっともらしい誤出力） 出力の検証と、人が承認する場面を定める
    Bias（偏り）・差別 対象者への影響、評価、説明、苦情対応を考える
    AI Agent（自律的に作業するAI） 操作範囲、最小権限、承認点、記録、停止権限を定義する
    外部モデル・サービスへの依存 供給者変更、データ由来、終了・代替手段、事故通知を確認する

    AIが判断に参加してもAccountability（説明責任）は消えません。NIST AI RMF（AIリスク管理枠組み）は、Govern（統治）、Map（状況把握）、Measure（測定）、Manage（管理）という機能で考える補完資料です。CSFの6機能と同じものではありません。NIST AI RMF

    Exam Perspective（試験での考え方）：新しい技術だから、最初に製品の導入や全面禁止と決めません。用途、データ、影響、権限、法的条件、管理策を確認し、許可される使い方と必要な教育を定めます。

    説明できるか：フィッシング訓練後に報告件数が増えたとき、悪化か改善かを判断するために必要な追加情報を説明してください。

    A.2 管理者による不正変更

    管理者はMFA（多要素認証）を利用していますが、自分で変更を申請・承認・実行し、ログも削除できます。

    考え方：本人確認を強めるだけでは職務上の不正を防げません。職務分離、特権の制限、独立した承認、ログの保護、独立レビューを検討します。調査では証拠保全と権限を確認し、事実と疑いを分けます。第2章・第5章・第8章

    一般原則：正しく認証された主体でも、過大な権限や検証不在はリスクです。

    A.3 安い対策と義務のある対策

    対策Aは予測損失の削減額より年間費用が大きいものの、適用法の要件を満たすために必要です。対策Bは純便益が正ですが、基幹業務を許容時間以上停止させます。

    考え方：Aは単純な純便益だけで却下できません。適法で負担の少ない実現手段を比較します。Bは便益が正でも業務要求を満たさず、そのまま採用できません。前提を調整するには権限者の判断が必要です。第4章・第7章・第9章

    一般原則：費用対効果は重要な判断材料ですが、法令・安全・事業の制約条件の中で用います。
